# 筋トレノート 要件

## 目的

自宅のインクラインベンチと可変式ダンベルで行う筋トレを記録し、
**前回より重く／多く挙げられているか**を判断できるようにする。

## 対象環境

| 項目 | 内容 |
|---|---|
| 利用端末 | iPhone 13 mini（論理幅 375px）／ iOS 26 |
| 形態 | PWA（Web アプリ）。ホーム画面に追加して使う |
| データ保存 | 端末内の IndexedDB のみ。サーバーへは一切送信しない |
| 利用者 | 本人1名 |

## 確定した仕様

### 記録する項目

- 日付（1日1セッション）
- 種目
- セットごとの **重量（ダンベル片手あたり）× 回数**
- RPE（主観的なきつさ 1〜10・任意）
- 休憩時間（直前のセットからの経過秒数を自動計測）
- ウォームアップかどうか
- その日のメモ・体重

### 記録しない項目

- **ベンチの角度**（利用者の判断で対象外）
- iCloud 同期（バックアップの書き出し／読み込みで代替）
- HealthKit 連携、Apple Watch 対応

### ダンベルの重量段階

所有している可変式ダンベルで実際に設定できる15段階を初期値とする。

```
2.5, 3.5, 4.5, 5.5, 6.5, 8.0, 9.0, 10.0, 11.5, 13.5, 16.0, 18.0, 20.5, 22.5, 24.0 (kg)
```

＋ / − ボタンはこの段階の間だけを移動する。設定画面から変更できる。

## 設計上の決定と、その理由

### 1日1ワークアウトに束ねる

同じ日付に複数セッションを作らず、1つのワークアウトへセットを追加していく。
自宅トレでは1日1回が基本であり、UI が単純になるため。
2部練の場合も同じ日のセットとして続けて記録できる。

### 重量は「ダンベル片手あたり」で保存する

ダンベルに表示されている数字をそのまま入力できるようにするため。
種目ごとに `dumbbellCount`（同時に使うダンベルの数）を持ち、
記録した重量が片手あたりであることを画面に添える。

- インクラインダンベルプレス（両手に1個ずつ）→ 2
- ワンハンドダンベルロウ（片手ずつ）→ 1
- ダンベルプルオーバー（両手で1個）→ 1

### 重量を上げる判断を自動化する（ダブルプログレッション）

利用者の主な困りごとは「前回何kgでやったか忘れる」「上げるか据え置くか迷う」の2点。
これを記憶と判断の両面から仕組みで解く。

**回数レンジの既定値は筋の構造で決まる**

種目ごとに、主に効かせる筋を「平行筋（紡錘状筋）」か「羽状筋」で分類し、
既定の回数レンジを次のように割り当てる。

| 分類 | 既定レンジ | 代表例 |
|---|---|---|
| 平行筋 | 10〜15回 × 3セット | 上腕二頭筋、広背筋、僧帽筋、ハムストリングス、腹直筋 |
| 羽状筋 | 8〜12回 × 3セット | 三角筋、大胸筋、上腕三頭筋、大腿四頭筋、下腿三頭筋 |

同じ部位でも筋によって分類が異なるため（腕なら二頭は平行筋・三頭は羽状筋）、
初期種目は**種目名ごと**に分類を持つ。自分で作る種目は部位の既定から始め、選び直せる。

**この対応づけの位置づけ:** 解剖学的分類にもとづく実践的な指針であり、
「この構造にはこの回数」という形で対照試験に裏づけられたものではない。
筋肥大は限界近くまで追い込めば広い回数域で起こるため、種目ごとに変更できるようにしてある。

**判定規則**

種目ごとに目標「repsMin〜repsMax回 × sets セット」を持つ。前回セッションについて、

1. 最も重い重量のセットを基準にする（軽い補助セットや落とした最終セットに引きずられないため）
2. その重量のセットが目標セット数以上あり、**すべてで repsMax 回に達していれば**重量を1段階上げる
3. 満たしていなければ据え置き、回数を伸ばす

**なぜこの方式か**

所有している可変式ダンベルは 11.5 → 13.5kg が +17% と刻みが粗い。
感覚で上げると潰れるため、上げる条件を明示的に固定する必要がある。
回数で伸ばしてから重量を上げるダブルプログレッションは、刻みの粗い器具と相性がよい。

**表示**

ホームの種目ごとに「今回も 11.5kg／全3セットで12回できたら次は 13.5kg」のように、
結論と次の条件を1行ずつ出す。増量できる回は罫線を濃くして見落としを防ぐ。

**思い出す導線**

種目を選ぶシートにも「前回 11.5kg（7/31）」を出し、追加する前に確認できるようにする。

### セット入力の初期値を引き継ぐ

「毎回同じ数字を入力し直す」手間を無くすため、次の順で初期値を決める。

1. 同じセッションの直前のセット
2. 上記の提案（据え置きなら前回の1セット目の回数、増量なら目標の下限回数）

RPE とウォームアップ指定はセットごとに変わるため引き継がない。

### 休憩時間は部位ごとに既定値を置く

筋肥大を目的とした休憩時間のメタ分析では、短い休憩（1分程度）より
**2分以上の休憩の方が同等かそれ以上**の結果になるとされる。
総挙上量（重量×回数×セット数）を維持できることが主な理由と考えられている。
一方、単関節・小筋群は回復が速く、60〜90秒でも総挙上量を保ちやすい。

そこで「動員される筋量と関節の数」に応じて段階的に既定値を置く。

| 部位 | 既定 | 理由 |
|---|---|---|
| 脚 | 180秒 | 動員される筋量が最大で、全身性の疲労が大きい |
| 背中 | 150秒 | 多関節・大筋群 |
| 胸 | 150秒 | 多関節・大筋群 |
| 肩 | 120秒 | プレス系は多関節、レイズ系は単関節 |
| 腕 | 90秒 | 単関節中心 |
| 体幹 | 60秒 | 低負荷・高回数になりやすい（現在は画面に出していない） |
| その他 | 120秒 | 中間 |

これは**新しく作る種目に適用される初期値**で、設定画面から部位ごとに変更できる。
種目ごとの実際の値はカルテ画面から個別に変更できる。

### 休憩の目安はセット単位で持つ

同じ種目でも、ウォームアップと本セットで必要な休憩は違う。
胸の既定は150秒だが、限界近くまで追い込まないウォームアップで
2分半待つのは長すぎる。

そのためセットごとに `restTargetSec`（そのセットの後に取る休憩の目安）を保存し、
休憩タイマーは**直前のセットに記録された値**を目標にする。

- 初期値は種目の設定。記録画面で ± 15秒ずつ動かせる
- 「ウォームアップ」に切り替えると 60秒（`WARMUP_REST_SEC`）まで自動で下がる。
  切り替えのたびに手で縮めるのでは操作が増えるため
- 種目の設定の方が短ければ、ウォームアップでも長くしない
- 次のセットの初期値には引き継がない。RPE やウォームアップ指定と同じく、
  セットごとに変わる値だから
- `restTargetSec` を持たない v5 より前のセットは、種目の設定で補う

### アラームの長さは選べるようにする

合図の音は Web Audio API で合成している（音声ファイルを持たずオフラインで鳴らすため）。
当初は 0.18秒 × 2回 の約0.5秒で、気づかないことがあった。

気づきやすさは人と場所で変わるため、長さを設定から選べるようにした
（1 / 3 / 6 / 12秒、既定は3秒）。

- 長い時間は**2回鳴らして少し空ける**の繰り返しにする。
  等間隔で鳴らし続けると、合図ではなく機械の警告音のように聞こえる
- 設定画面では**選んだ瞬間にその長さで鳴らす**。
  秒数だけ見せられても、実際の長さは判断できない

### 休憩タイマーはアプリ全体の枠に置く

休憩中に履歴やグラフ、食事の記録を見るのは普通の使い方で、
ホーム画面の中に置くと画面を移った瞬間にタイマーもアラームも止まる。
`AppShell` から呼び、どの画面にいても動き続けるようにした。

これに伴い、セットに保存する休憩秒数（`restSec`）は画面のタイマーから受け取るのをやめ、
**直前のセットの記録時刻との差**として保存時に求める。
どの画面から記録しても同じ値になり、タイマーの表示状態にも依存しない。

### 選んだ種目は端末側に覚えさせる

メニューから種目を選んだだけの状態では、まだ1セットも記録していない。
この時点で DB にワークアウトを作ると、記録の無い日が増えてしまう。
かといって画面の state だけで持つと、履歴やグラフを見に行った時点で選択が消える。

そこで localStorage に日付ごとに持たせた（`usePendingExercises`）。
画面を移っても、アプリを開き直しても残る。溜まり続けないよう直近7日ぶんだけ残す。

### 休憩タイマーは「経過時間の再計算」で実装する

iOS の Web アプリは、画面ロックやバックグラウンドで JavaScript が止まる。
そのため、タイマーはカウンタを increment するのではなく、
**開始時刻と現在時刻の差分**を毎回計算する。
これにより、アプリに戻ったときに正しい経過時間が表示される。

### 休憩終了は音で知らせる（画面を点けたままにする）

iOS の Web アプリは画面がロックされると JavaScript が止まるため、
そのままでは休憩終了のアラームを鳴らせない。

そこで **休憩中だけ Screen Wake Lock で画面を消えないようにする**。
これにより、アプリを開いたまま置いておけば確実に鳴る。
目標時間に達したらロックを解放し、電池の消費を抑える。

音は Web Audio API で合成する（音声ファイルを持たないため、オフラインでも確実に鳴る）。
iOS は利用者の操作を起点にしないと音を出せないので、
セットを記録したタイミングで AudioContext を解錠しておく。

目標到達から10秒を過ぎてからアプリに戻った場合は鳴らさない。
終わった休憩に対して鳴らしても驚かせるだけのため。

**残る制約:** 他のアプリを見ている間や、利用者が明示的に画面を消した場合は鳴らない。
設定でこの機能をオフにできる（その場合は画面も点けたままにしない）。

### 画面は白黒のみで構成する

色を使わないぶん、色で伝えていた情報は別の手段に置き換える。

| 伝えたいこと | 置き換えた手段 |
|---|---|
| 選択中のタブ | 文字色の濃さ＋太字 |
| 取り消せない操作（削除） | 他より太い枠線 |
| 注意（バックアップ未実施） | 左端の太い罫線＋地色 |
| 入力エラー | 太字＋下線 |
| ウォームアップのセット | 破線の枠 |
| グラフの2系列 | 濃さ＋線種（実線／破線）。凡例も線種を反映する |
| 休憩の目安到達 | バーが満了し、文字が濃くなる |

配色は iOS の外観設定に連動する（`prefers-color-scheme`）。
CSS 変数を役割名で定義し、ダーク用ブロックで値だけを差し替えている。
グラフは SVG 属性として色を渡す必要があり CSS 変数が使えないため、
`useColorScheme` フックで外観を読み、`chartPalette.ts` の配色を選ぶ。

### フォームの参考リンクは「検索を既定」にする

種目ごとに参照先の URL を保存できるが、**未設定でも使える**ことを優先する。
未設定の種目は「種目名 + フォーム」での YouTube 検索を開く。
これにより28種目すべてが事前設定なしで参照でき、
良い動画が見つかった種目だけ URL を保存して差し替えられる。

**セキュリティ上の扱い:** 保存された URL はそのままリンクの `href` に入るため、
`javascript:` や `data:` のようにクリックで実行され得るスキームを保存時に弾く。
取り込んだバックアップに不正な値が混ざっていた場合に備え、
表示時にも再検証し、危険な値なら検索へフォールバックする。
外部サイトへは `target="_blank"` と `rel="noopener noreferrer"` で開く。

### 記録し忘れた日を後から入力できる

ホームは今日だけを扱うが、履歴から日付を選べば過去の日も同じ操作で記録できる。
編集の仕組みは `useWorkoutEditor` に集約し、日付だけを差し替えて両方の画面で使う。

**記録時刻の扱い:** 過去の日付を入力するとき、現在時刻をそのまま使うと
「最も新しい記録」の判定が実際の実施順と食い違う。
そのため当日以外はその日の正午を記録時刻にする（`buildRecordedAt`）。

過去の日については、これから行う重量の提案は意味を持たないため表示しない。

### 記録を失わないための備え

記録は端末内にしか無く、失うと取り返せない。

- 起動時に永続ストレージを要求し、空き容量不足での削除対象になりにくくする
- バックアップの督促は設定画面だけでなく**ホーム画面にも出す**（設定画面は自分から開かないため）
- 守るべき記録がまだ無いうちは督促しない

### 週あたりの部位別セット数

総挙上量(kg)は達成感の指標にはなるが、「次に何をすべきか」には使いにくい。
部位ごとの週間セット数は、足りていない部位がそのまま次の行動になる。

筋肥大では1部位あたり週10〜20セット程度で用量反応が見られるとするレビューが多く、
実務上の目安として広く使われている。この範囲を帯で示し、今週と先週を並べる。
週の始まりは月曜。

### 画面に出ている値をそのまま保存する

重量は ± ボタンでダンベルの段階からしか選べないが、保存時に段階へ丸め直すことはしない。
丸めると、ダンベルの設定を変えたあとに既存のセットを開いただけで、
表示と違う重量に書き換わってしまうため。

### シートの初期化は「開いた瞬間」だけ

ホーム画面は休憩タイマーのために毎秒再描画される。
シートの初期値を「値の同一性」で監視すると、再描画のたびに入力中の内容が
初期値で上書きされ、メモや体重を入力できなくなる。
そのため初期化は開いた瞬間だけに限定する（`useResetOnOpen`）。

### 種目づくりで聞くのは名前と部位だけにする

種目を作るときに器具・回数レンジ・休憩時間・筋の種類まで聞くと、
作るたびに5つの判断を迫られ、種目を増やすこと自体が億劫になる。
そこで**名前と部位だけ**を聞き、残りは部位から自動で決める
（回数レンジは `DEFAULT_ARCHITECTURE_BY_MUSCLE_GROUP`、休憩時間は
`DEFAULT_REST_SEC_BY_MUSCLE_GROUP`、器具はダンベル・両手に1個ずつ）。

自動で決めた値は**すべて種目カルテから変更できる**。特に `dumbbellCount` は
記録した重量が片手あたりか両手合計かの解釈が変わるため、作成後に直せる必要がある。

作成の入口は「種目を選ぶシート」と「設定 → 種目の管理」の2か所に置く。
一覧に無いと気づくのは種目を探している最中なので、そこで行き止まりにせず、
検索していた語をそのまま名前の初期値にして作れるようにする。

### 一意な名前は、書き込む前に確認する

`exercises.name` は一意索引だが、重複する `add` をそのまま発行してはいけない。
失敗した書き込みは Dexie の liveQuery の楽観更新を壊し、
購読しているコンポーネントごと落ちる（`Cannot read properties of null`）。
`createExercise` は追加の前に同名を検索し、`ValidationError` で先に弾く。

### 総ボリュームは表示しない

「重量 × 回数 × ダンベル数」の合計は、同じメニューを反復する人の疲労管理には
使えるが、日によって種目構成が変わると数字が大きく揺れ、増減が上達を意味しない。
筋肥大との対応も**セット数**の方が明確なため、
「今週の部位別セット数（10〜20セットが目安）」に一本化した。

### 下部タブは「系統の切り替え」にする

運動と食事はほぼ別のアプリで、必要な画面もそれぞれに4つある。
横に並べると1タブ62pxまで縮み、どちらも窮屈になる。

そこで**左端で系統を切り替え、右端の設定だけを常設**にした。
中央の4つは系統ごとに入れ替わる。

| 系統 | タブ |
|---|---|
| 運動 | ホーム / 履歴 / グラフ / メニュー |
| 食事 | 今日 / 履歴 / グラフ / 献立 |

- 切り替えボタンには**行き先**を出す。今いる側を出すと押した結果が読めない
- どちらの系統かは URL から決める（`/meals` 以下が食事）。
  設定画面はどちらにも属さないため、直前の系統のタブを出したままにする
- 直前の系統は localStorage に持つ。再訪時に運動側へ戻されないようにするため

### 食事は「食材から計算する」に絞る

日本食品標準成分表（八訂）増補2023年（文部科学省）を同梱し、
可食部100gあたりの値に量を掛けて計算する。出典表記のみで二次利用できる。

対象を食材に絞ったのは、成分表に**市販品と外食が収載されていない**ため。
バーコードや外食メニューを扱うには継続的に更新される商品データベースが要り、
無料・バックエンド無しという前提では持てない。
自炊が中心なら成分表でほぼ賄え、賄えない分（プロテイン等）はマイ食品で補う。

- 検索は「読み替え＋AND一致」。成分表は「ぶた」「にわとり」とひらがなで、
  かつ「にわとり ［若どり・主品目］ むね」と離れて書かれる。
  単純な部分一致では「鶏むね」が引けず、「にわとり」だけで引くと ささみ まで出る
- 記録には**その時点の栄養価を焼き付ける**。成分表の改訂やマイ食品の修正で
  過去の記録が書き換わってはいけない
- 未測定（`-`）と微量（`Tr`）は 0 として扱い、その旨を設定画面に書く

### 献立と「前の日と同じ」で入力を省く

毎日ほぼ同じものを食べる日が多く、そのたびに検索し直すのは無駄が大きい。

- **献立**: よく食べる組み合わせを登録し、1タップで区分ごと投入する
- **前の日と同じにする**: その日にまだ記録が無く、前日に記録があるときだけ出す
- **よく食べるもの**: 検索語が空のとき、記録回数の多い食品を先に並べる

いずれも投入するのは**保存済みの栄養価**で、成分表を引き直さない。
記録は「その時点の値を焼き付ける」という方針をここでも通す。

### 消費カロリーは METs から見積もる

厚生労働省の式で計算する。

```
エネルギー消費量(kcal) = 1.05 × METs × 時間(h) × 体重(kg)
```

- **有酸素**: 速度から METs を引く（Compendium of Physical Activities 2011）。
  表にない速度は前後から直線補間し、範囲外は端で頭打ちにする。外挿すると非現実的になる
- **筋トレ**: セッション全体で 3.5 METs。Compendium は連続実施を前提に 6.0 前後を当てるが、
  ここで数える時間はセット間の休憩を含むため、休憩込みの平均としては 3.5 が実態に近い
- **時間**: 最初と最後のセットの間隔に、セット間の平均間隔を1つ足す。
  そのままだと最後の1セットぶんが抜けるため
- **体重**: その日に測っていなければ直近の記録を使う。一度も無ければ 0 のままにし、
  当て推量の数字は出さない

同じ距離なら、ペースが違っても消費はおおむね変わらない（およそ 1kcal/kg/km）。
速くすると強度は上がるが時間が短くなり、打ち消し合うため。

「摂取 − 消費」は、体組成計で測った基礎代謝量を入れているときだけ出す。
基礎代謝をこちらで推定すると、誤差の上に誤差を重ねることになる。
日常生活の活動量は含まないため、画面に「目安」と明記する。

### 体組成は独立した記録にする

体重はワークアウトに載せていたが、体組成を測る日と鍛える日は一致しない。
`measurements` テーブルへ分け、1日1件（同じ日に測り直したら上書き）にした。
v8 の移行でワークアウトに入っていた体重を移している。

体組成計との Bluetooth 連携はできない（iOS Safari は Web Bluetooth 非対応）。
表示された数字を写す前提で、入力欄を体組成計の表示順に並べている。
体重以外は任意で、入れた項目だけがグラフに出る。

### ランニングの GPS 記録は作らない

iOS の Web アプリは画面ロック中に位置情報を取得できない。
ロック後は1度だけ粗い位置が返り、以降は約15分間隔の近似値になる仕様のため、
軌跡もスプリットも残せない。Screen Wake Lock で画面を点け続けるのは
電池と誤操作の面で現実的でない。

これはプラットフォームの制約で、実装の工夫では解決できない。
軌跡の自動記録は既存のアプリ（STRAVA など）に任せる。

そのうえで、**距離と時間の手入力**は受け付ける。
入力さえあればペース・速度・推定消費カロリーは出せるうえ、
食事の記録と同じ画面で収支を見られる価値があるため。

### 使わない部位は「型から消さず、画面から消す」

鍛えていない部位を並べても、種目を選ぶときの邪魔になり、
週間セット数では常に0の行が居座るだけになる。
一方で `MuscleGroup` から値を消すと、その部位を持つ過去の記録が
どこにも属さなくなり、表示名すら引けなくなる。

そこで2つの一覧に分ける。

| 定数 | 用途 |
|---|---|
| `MUSCLE_GROUPS` | 保存できる部位。使わなくなった部位も残す |
| `DISPLAYED_MUSCLE_GROUPS` | 画面に出す部位と並び順 |

現在 `core`（体幹）は保存はできるが画面には出していない。
`DISPLAYED_MUSCLE_GROUPS` に戻せば、設定・グラフ・種目の選択肢に再び現れる。
既存のデータベースに残る体幹の種目もそのまま復活する。

### 種目は削除せずアーカイブする

過去の記録が種目を参照しているため、削除すると履歴の表示が壊れる。
一覧から隠す「アーカイブ」で対応する。

## 既知の制約

| 制約 | 対応 |
|---|---|
| 画面ロック中に休憩終了を通知できない | 復帰時に正しい経過時間を表示する |
| 端末のストレージ都合でデータが消える可能性がある | バックアップの書き出しと、一定期間書き出していない場合の警告 |
| 日付をまたいで開きっぱなしにすると日付がずれる | 画面復帰時に日付を取り直す |
